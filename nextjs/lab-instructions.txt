1. Separate containers for frontend, API, and database (3-tier architecture)
The instructions just say "Dockerize the application" and "use a Dockerfile structure similar to the lab." In the recording, the lecturer is explicit that a single-tier or two-tier setup will lose marks — you need three separate services (frontend container, API/backend container, database container) wired together via Docker Compose, not everything bundled into one Dockerfile/container.

2. Choice of SQLite (via Sequelize) or Prisma/Postgres — either is fine
The brief only says "a suitable database tool or ORM such as Prisma," which reads like Prisma is expected. In the lab, the lecturer says you can use either SQLite (Sequelize) or Prisma/Postgres — no marks difference either way — and even recommends the SQLite/Sequelize version (Part 1 of the lab) as the simpler path.

3. Specific health check requirement: /health returning plain 200
The instructions do mention demonstrating "the health API returning 200 OK at /health," but the lab clarifies the intent: it should be a minimal endpoint that just confirms the server/Docker container is up and reachable — not a complex status/monitoring endpoint. This ties into later assessments (instrumentation), so keep it simple now.

4. Don't store phoneme characters or static reference data in the database
This is a notable gap. A student asked directly whether phoneme data needs to be in the database, and the lecturer said no — phoneme symbol sets are static and can stay in the frontend/a config; what actually needs to persist in the database is the word list itself (the phoneme-based words, and possibly their English equivalents), the activity name, and settings — not the character-encoding table. He also noted the puzzle grid itself doesn't need to be stored — only the word list, since the layout can be regenerated.

5. Environment variables / credentials handling
Not mentioned in the brief at all. The lecturer says:

Don't hardcode DB usernames/passwords in the Dockerfile or docker-compose.yml — use a .env file instead.
He's not deducting marks heavily for this yet (encryption of env vars is a later-assessment topic), but he flags it as something reviewers will notice under code quality/GitHub review.

6. GitHub practices
Also not in the brief: he wants the .git folder included in your submission/repo history (not just a code dump), and dislikes seeing everything done in one or two giant commits (a signal of just pasting in AI-generated output without iterating). He ties this to the "code quality" part of the rubric.

7. Update the README from Assessment 1
He specifically says to update the README file — this is implied but not stated in the written brief.
